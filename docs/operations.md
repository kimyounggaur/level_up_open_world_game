# 운영 절차 (8-6)

설계서 12.11의 8-6("운영 절차: 콘텐츠 판 올리기, 저장 변환 테스트, 문제 있는 콘텐츠 내리기")의 근거 문서다. 완료 기준은 "이전 기록을 새 정답 기준으로 다시 계산하지 않는다"이다.
이 문서가 적는 것은 **코드와 시험으로 확인한 절차**다. 어떤 콘텐츠를 올리고 내릴지, 공개해도 되는지는 사람이 정한다. 아래 도구는 그 판단을 대신하지 않고, 실수로 이미 나간 기록의 뜻을 해치는 것만 막는다.

## 한눈에

| 하려는 일 | 하는 법 | 기계가 막는 것 |
|---|---|---|
| 정답 기준을 고친다(악보, 판정, 묻는 말, 틀렸을 때의 말) | 그 과제 파일의 `contentVersion`을 올린다 → `npm run lock:content` → `npm run verify` | 판을 올리지 않고 고치면 `LOCK_CHANGED`, 판을 내리면 `LOCK_VERSION_DOWN` |
| 문제 있는 과제를 내린다 | `availability`를 `"draft"`로 바꾸고 다시 내보낸다. 파일은 지우지 않는다 | 파일을 지우면 `LOCK_REMOVED` |
| 내렸던 과제를 다시 올린다 | 사람이 검수 기록을 확인한 뒤 `availability`를 `"published"`로 | 검수·출처·권리가 끝나지 않았으면 `npm run validate`가 막는다 |
| 저장 형식을 바꾼다 | 아래 "저장 형식 바꾸기" | 변환이나 얼린 예시가 없으면 `tests/unit/save-compat.test.ts`가 실패한다 |
| 정식 공개 빌드를 낸다 | `npm run verify` → `npm run build:release` | 공개 점검(`npm run check:release`)이 막으면 빌드를 시작하지 않는다(8-5) |

## 이전 기록은 다시 계산하지 않는다 (완료 기준의 근거)

이 기준은 다섯 가지 사실이 함께 만든다. 앞의 넷은 코드가 그렇게 되어 있다는 것이고, 마지막이 이번 단계에서 더한 잠금이다.

1. 시도 기록(`AttemptResult`)은 시도한 순간의 `contentVersion`과 판정 결과(`resultType`)를 함께 저장한다(`src/domain/attempt.ts`).
2. 통과는 저장된 `resultType`에서 읽는다. `isPass`는 `resultType === 'passed'`만 보고, 기록을 정답 기준으로 다시 판정하는 코드는 없다.
3. 등불, 지역의 소리 층, 합주 층수는 저장하지 않고 통과 기록과 지도에서 매번 계산한다(`computeReaction`, 10.6). 공개 상태나 정답 기준을 보지 않는다. 그래서 과제를 내리거나 판을 올려도 이미 얻은 것은 줄지 않는다(W-6).
4. 저장의 `contentVersions`는 **저장하는 순간 앱이 가진 판**이다. 저장에 이름이 오른 과제(열어 본 것, 초안이 있는 것, 기록이 있는 것) 가운데 지금 목록에 있는 것만 적는다. 시도마다 적힌 `contentVersion`은 그 시도를 한 순간의 판이다. 둘이 다르면 "그 뒤에 판이 올랐다"는 뜻이지 기록이 틀렸다는 뜻이 아니다.
5. 정답 기준이 바뀌었는데 판 번호가 그대로이면, 옛 기록이 어느 기준으로 통과했는지 알 수 없게 된다. **내용 잠금**(`content/content-lock.json`)이 이것을 막는다.

## 콘텐츠 판 올리기

### 정답 기준이란

과제마다 `answerBasisOf`(`src/domain/contentlock.ts`)가 정한다.

- 판본마다: `challengeDescriptor`(무엇을 묻는가), `score`(목표 악보), `evaluatorSpec`(판정)
- 과제의: `feedbackRules`(틀렸을 때 보이는 말). 같은 시도가 다른 말로 보이게 되므로 정답 기준에 넣었다.
- 판본이 더해지거나 빠지는 것도 정답 기준이 바뀐 것이다.

정답 기준이 **아닌** 것: `label`, `availability`, `title`, `topicTags`, `sourceRefs`, `placements`, `assistanceLinks`, 검수 기록. 이것을 고치는 일(내리고 다시 올리기, 검수 기록 고치기, 배치 옮기기)에는 판을 올리지 않는다.
키 순서는 상관없다. 기준의 해시(sha256 앞 16글자)는 키를 정렬한 글자에서 만든다.

### 순서

1. 과제 파일(`content/quests/<과제 id>.json`)에서 정답 기준을 고친다.
2. 같은 파일의 `contentVersion`을 올린다. 세 자리 숫자(`0.1.0` → `0.2.0`)이고 앞에서부터 견준다. 어느 자리를 올릴지는 정하지 않았다(D-297). 올리기만 하면 되고, 내리는 것은 막힌다.
3. `npm run lock:content`로 잠금에 기록한다. 쓰기 전에 이미 나간 판의 뜻을 해치는 어긋남이 있으면 쓰지 않고 이유를 보인다.
4. `npm run verify`로 전체를 확인한다. `npm run validate`(`verify`와 `build`가 부른다)도 잠금 파일이 있으면 같은 점검을 한다.

`npm run check:lock`은 쓰지 않고 견주기만 한다. 어긋나면 1로 끝난다.

### 도구가 말하는 것

| 코드 | 뜻 | `lock:content`가 쓰는가 | 고치는 법 |
|---|---|---|---|
| `LOCK_CHANGED` | 정답 기준이 바뀌었는데 판이 그대로다 | 쓰지 않는다 | 판을 올린 뒤 `lock:content`. 고칠 뜻이 아니었으면 되돌린다 |
| `LOCK_VERSION_DOWN` | 판 번호가 내려갔거나 견줄 수 없는 모양이다 | 쓰지 않는다 | 판 번호를 잠금의 것 이상으로 |
| `LOCK_REMOVED` | 잠긴 과제의 파일이 없다 | 쓰지 않는다 | 파일을 되돌리고 `availability`를 `"draft"`로 |
| `LOCK_STALE` | 판이 올랐는데 잠금은 옛것이다 | 쓴다 | `lock:content` |
| `LOCK_NEW` | 잠금에 없는 새 과제다 | 쓴다 | `lock:content` |
| `LOCK_MISSING` | 잠금 파일이 없다 | 쓴다(처음 만든다) | `lock:content`. `npm run validate`는 파일이 없어도 통과하고, 공개 점검만 파일을 요구한다 |
| `LOCK_SHAPE` | 잠금 파일이 형식에 맞지 않거나 JSON이 아니다 | 쓰지 않는다(읽을 수 없다고 끝난다) | 파일을 고친다. 지우고 새로 만드는 것은 지금 콘텐츠를 기준으로 받아들이는 일이라 정답 기준을 고치지 않았다고 확신할 때만 한다 |

앞의 셋(`LOCK_CHANGED`, `LOCK_VERSION_DOWN`, `LOCK_REMOVED`)이 "이미 나간 판의 뜻을 해치는" 것이라 잠금을 새로 쓰는 것도 막는다. 잠금을 손으로 고쳐 통과시키는 것은 도구가 막지 못한다: 잠금 파일은 사람이 책임지는 기록이다.

### 판을 올린 뒤 저장에서 벌어지는 일

- 이미 쌓인 시도 기록은 그대로다. 시도의 `contentVersion`도, 통과 여부도 바뀌지 않는다.
- 다음 저장부터 `contentVersions`에 새 판이 적힌다(위 4번).
- 저장된 초안은 그대로 남고 새 판에서도 열린다. 새 판의 틀과 맞지 않는 초안이 어떻게 보이는지는 이 단계에서 시험하지 않았다(아래 한계).

## 문제 있는 콘텐츠 내리기

**내린다는 것은 `availability`를 `"draft"`로 바꾸는 것이다.** 파일을 지우지 않는다.

| 내릴 것 | 바꾸는 곳 |
|---|---|
| 과제 전체 | `content/quests/<과제 id>.json`의 `availability` |
| 판본 하나 | 같은 파일 `variants.<판본 id>.availability`(판본에 적힌 값이 과제의 값보다 앞선다) |
| 소리 조각, 쪽지, 놀이 악기 | `content/discoveries/*.json`의 그 항목 `availability` |

정식 공개(release) 채널에서는 그 판본이 '준비 중'이 되어 고를 수 없고, 그 주소로 들어오면 과제 목록과 함께 "이 과제는 준비 중이에요. 검수가 끝나면 열려요."가 보인다. 미리보기(preview) 채널에서는 '검수 전' 표지를 달고 열린다(`stateOf`와 `ContentCatalog.resolve`, `src/domain/catalog.ts`). 그러므로 내리는 일은 공개 채널에만 뜻이 있다.

내려도 남는 것:

- **저장된 초안과 시도 기록.** 사용자의 기기에 있는 저장은 건드리지 않는다. 다시 올리면 초안이 돌아온다.
- **이미 통과한 것으로 계산된 등불과 소리 층.** 통과 기록에서 계산하는 값이라 줄지 않는다(W-6, 10.6).
- 자유 선율(과제가 아닌 길)은 과제의 공개 상태와 상관없이 열린다.

내릴 때 하지 않는 것:

- 파일을 지우지 않는다. `LOCK_REMOVED`로 막히고, 저장된 기록이 그 과제 id를 가리키고 있다. 지워야 한다면 저장 형식을 바꾸는 일로 따로 설계한다.
- 정답 기준을 고치지 않는다. 내린 동안 고쳐도 판을 올려야 하는 것은 같다.

다시 올릴 때는 사람이 검수 기록을 확인하고 `availability`를 `"published"`로 바꾼다. 검수 단계가 끝나지 않았거나 출처가 미확인이면 `npm run validate`가 막는다.

내린 것을 사용자에게 닿게 하려면 새 빌드를 올리거나 호스트의 이전 배포로 되돌린다(`docs/hosting.md`). 이미 열어 둔 탭은 다시 읽을 때까지 옛 콘텐츠를 가진다.

**코드가 만든 소리**(광장 합주, 지역 바탕 소리, 정거장 서명 소리)는 과제처럼 `availability` 스위치가 없다. 공개 전에 막는 방법은 출처·권리 대장의 `snd.music.world-parts`가 미확인인 동안 `npm run check:release`가 `build:release`를 막는 것(D-295)뿐이다. 이미 공개한 뒤에 문제가 생긴 소리는 코드를 고쳐서 다시 내보내야 한다.

## 저장 형식 바꾸기

저장 형식(`SAVE_SCHEMA_VERSION`, 지금 1)을 바꾸는 날의 절차다. 지금은 판이 하나뿐이라 변환이 하나도 없고, 길과 시험만 먼저 깔려 있다.

1. `src/domain/save/save.ts`의 `SAVE_SCHEMA_VERSION`을 N에서 N+1로 올린다.
2. 같은 파일의 `SAVE_MIGRATIONS[N]`에 N판의 저장(JSON 객체)을 N+1판의 저장으로 바꾸는 함수를 쓴다. 받은 객체를 고치지 않고 새 객체를 돌려준다. 판 번호는 `migrateSaveRaw`가 한 판씩 올리므로 함수가 적지 않아도 된다. `parseSave`가 읽을 때마다 이 변환을 거치므로, 파일 가져오기와 저장소에서 읽는 것 모두 같은 길을 지난다.
3. `tests/fixtures/saves/`에 N+1판 앱이 내보낸 저장의 예시를 새 파일로 더하고, `tests/unit/save-compat.test.ts`의 `FROZEN`에 파일 이름, 판, sha256을 적는다. **옛 예시는 고치지 않는다**(해시가 지킨다). 이 예시가 "이미 나간 판의 저장을 지금 앱이 읽는다"를 지키는 시험의 입력이다.
4. `npm run verify`. 빠뜨리면 실패하는 것: 변환이 빠진 판(`SAVE_MIGRATIONS`), 판마다 있어야 하는 얼린 예시, 얼린 예시를 고친 것, 목록에 없는 예시 파일.

**저장 키에 판 번호가 들어 있다**(`levelup-music-world:v1:save:*`, D-6, D-104). 그래서 N+1판 앱은 새 칸(`v(N+1)`)을 쓰고, 옛 칸은 이렇게 다룬다.

- 새 칸이 **모두 비어 있을 때만** 옛 칸(가까운 판부터)을 읽는다. 한 판 안에서는 현재, 임시, 긴급 가운데 가장 새것을, 없으면 직전을 연다. 엄격한 검사를 통과하는 것만 쓴다.
- 읽은 글자는 옛 판의 모양 그대로 앱에 넘기고, 앱의 첫 저장이 새 칸에 새 모양으로 적는다. 그 뒤로는 새 칸이 이긴다.
- 옛 칸은 **읽기만 한다.** 덮지도 지우지도 않는다. 앱을 옛 판으로 되돌려도 옛 저장이 그대로 있다. 되돌린 옛 앱은 새 칸을 읽지도 덮지도 않는다(D-104).
- 사용 기록(`usage-log`)의 키에도 판 번호가 있어서 같은 길로 옛 키의 기록을 이어 받는다. 설정의 '기록 지우기'(`UsageLog.clear`)는 옛 키의 기록과 따로 둔 읽을 수 없는 기록도 함께 지운다. 읽기만 하던 옛 키를 지우는 코드는 `SaveStorage.clear`와 `UsageLog.clear` 둘뿐이다.
- 사용자가 저장을 지우면(`SaveStorage.clear`) 옛 칸도 지운다. 남겨 두면 다음에 읽을 때 되살아난다. 지금 앱에는 이 단추가 없다(`docs/privacy-flow.md`).

바꾸지 않고 두는 것: 옛 칸에 읽을 수 없는 저장만 있으면 새로 시작하고 옛 칸은 건드리지 않는다. 새 칸에 읽을 수 없는 저장이 있으면 옛 칸은 보지 않는다(기존 복구 길이 먼저다).

## 월드에 새 그래픽 층을 더할 때 (8-4가 넘긴 일)

월드에서 한 번 그려 두는 그래픽(등불, 소리 조각·쪽지 자리, 주민, 놀이 악기의 바닥)은 화면 밖에서 그려지지 않게 `ViewCull`이 맡는다(`src/world/cull.ts`, D-289). 새 층을 더하면 이렇게 한다.

1. 한 번 그려 두는 그래픽이면 `ViewCull.track(그래픽, 범위)`로 맡기고, 층을 걷을 때 `untrack`한다. 맡기지 않아도 화면은 같다. 대신 화면 밖 그림을 프레임마다 다시 그리는 낭비가 생긴다(8-4에서 이 낭비가 프레임 하나에 스크립트 시간을 평균 22.1 ms 썼다).
2. 범위(`box`)는 그 그래픽이 그려지는 월드 범위를 덮게 잡는다. 작게 잡으면 보여야 하는 그림이 사라질 수 있다.
3. 매 프레임 다시 그리는 층(설치물 층처럼 그래픽 하나를 모두가 나눠 쓰는 것)은 `track`을 쓰지 않고, 그리는 자리마다 그릴지 정한다(`src/world/installations/layer.ts`, 안 그리는 자리는 `NO_DRAW`가 호출을 받아 버린다).
4. `npm run build` 뒤 `tests/flow/cull.flow.ts`를 돌린다(실제 Chrome. 정거장 23곳과 설치물 모드에서 건너뛰기 켬·끔·켬 세 장을 화소로 견준다). 새 층이 한 화소라도 달라지게 하면 실패한다. 이 시험은 서 있는 화면과 바로 이동한 첫 프레임, 설치물 모드의 정지 화면만 본다. 걷는 중이나 움직이는 그림은 보지 않는다.

## 정식 공개 빌드 내보내기

```
npm run verify            # 의존 규칙·콘텐츠·형식·단위 시험
npm run lock:content      # 정답 기준을 고쳤다면(위 "콘텐츠 판 올리기")
npm run build:release     # 공개 점검 → 콘텐츠 검사 → 형식 검사 → dist-release/
```

`build:release`는 `npm run check:release`를 먼저 부른다. 점검이 막으면 빌드를 시작하지 않는다. 막는 것은 기계가 볼 수 있는 조건뿐이다.

- 정식 공개 채널에서 열리는 과제가 0개
- 출처·권리 대장에서 권리가 미확인인 항목(지금 `snd.music.world-parts` 하나)
- 내용 잠금 파일이 없거나 지금 콘텐츠와 어긋남
- 막다른 길 끝 가운데, 정식 공개 채널에서 보이는 발견 요소(공개 상태인 것)가 200 px 안에 없는 곳(3.4의 규칙 2). 월드에 8곳이고 지금은 발견 요소가 모두 검수 전이라 8곳 모두다. 막는 문장이 그 끝에서 가장 가까운 발견 요소의 id와 거리를 적으니, 그것이 검수와 권리 확인을 마치고 공개 상태가 되면 채워진다. `npm run validate`의 `DEAD_END` 검사는 공개 상태와 상관없이 파일 전체를 보므로 이 조건과 따로다

점검이 통과해도 **G2가 통과한 것이 아니다.** 사람이 하는 일(관찰, 음악 검수, 음색 듣기, 교재 대조와 권리 확인, 접근성 사람 점검, 기준 기기, 호스팅·법률, 공개 승인)은 점검이 대신하지 않아서, 결과에 목록을 늘 함께 낸다(`src/domain/release.ts`의 `HUMAN_RELEASE_STEPS`). 올리는 방법과 호스팅 머리말은 `docs/hosting.md`를 본다.

## 사람이 상태를 바꾸는 곳

사람이 확인을 마치면 아래를 바꾼다. 이 값들은 도구가 대신 바꾸지 않는다(D-4, D-13).

| 바꾸는 것 | 어디 | 바꾸면 고쳐야 하는 시험 |
|---|---|---|
| 검수 단계를 끝냈다 | `content/sources/review-log.json`의 그 항목을 `"status": "done"`, `by`(확인한 사람), `at`(YYYY-MM-DD)로 | `review-checklist.test.ts`의 "사람이 하는 단계는 자동으로 완료가 되지 않는다" |
| 출처를 확인했다 | 과제 파일 `sourceRefs[]`의 `reviewStatus: "reviewed"`, `rightsStatus: "confirmed"` | `content.test.ts`의 "아직 사람이 확인하지 않은 것은 모두 draft와 pending이다" |
| 공개한다 | 과제·판본·발견 요소의 `availability: "published"` | 위 시험과 `discovery.test.ts`, `discovery-regions.test.ts`의 "모두 미리보기에만 보인다" |
| 코드가 만든 소리를 승인했다 | 대장 `content/sources/asset-ledger.json`의 `snd.music.world-parts`: `rights`를 `own`(또는 `licensed`)으로 고치고 `gate`를 지우고 `checkedOn`을 적는다. `license`의 '권리 확인 전'도 확인한 근거로 고친다 | `ledger.test.ts`의 "미확인 항목은 하나뿐이고…" |

이 시험들은 사람의 단계가 자동으로 넘어가지 않게 지키는 시험이다(D-113). 사람이 일부러 상태를 바꾸면 실패하는 것이 맞고, 그때 시험의 기대를 새 상태로 고친다. `availability`와 검수 기록은 정답 기준이 아니라서 공개하는 데에는 판을 올리지 않는다.

## 알려진 한계

- **내용 잠금은 사람이 책임지는 기록이다.** 잠금 파일을 손으로 고치면 도구는 그것을 기준으로 삼는다.
- **잠금이 보는 것은 정답 기준뿐이다.** 판정기의 코드(`src/domain/evaluators/`)를 고쳐서 같은 `evaluatorSpec`이 다르게 판정하게 되는 것은 잠금이 보지 못한다. 판정기를 고칠 때는 영향받는 과제의 판을 사람이 올린다.
- **새 판의 틀과 맞지 않는 초안**(예: 칸이 줄어든 판본)이 어떻게 보이는지는 시험하지 않았다.
- **저장 변환은 아직 하나도 없다.** 길(`SAVE_MIGRATIONS`, 옛 칸 읽기)과 얼린 예시 시험은 있지만, 실제 변환을 거치는 예시는 첫 개정 때 생긴다. 그때 이 문서의 절차를 한 번 따라 해 보고 고칠 곳을 적는다.
- **이미 열어 둔 탭**은 새로 읽을 때까지 옛 콘텐츠를 가진다. 강제로 바꾸는 길은 없다.
- 판 번호 자리의 뜻(앞, 가운데, 뒤)은 정하지 않았다(D-297).
