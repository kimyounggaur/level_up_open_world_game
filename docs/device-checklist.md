# 기기 손 점검표 (8-3, 8-4)

설계서 12.11의 8-3("기준 기기 전체 점검 | 10.8의 손 점검표"), 10.8("손 점검 | 점검표 | 기준 기기에서 소리, 터치, 화면 회전, 무음 스위치"), D-2("주 기기: 가로 태블릿과 PC. 기준 기기 3종은 미정")의 문서다. 8-4(용량과 불러오기 시간 맞추기, 10.7의 목표)가 프레임 속도를 재는 방법(P3)과 항목 셋(S11, P5, P6)을 더했고, 8-5(공개 조건 점검)가 P6에 두 번째 방문과 보안 정책 확인을 더했다.

이 표는 **사람이 기준 기기에서 직접 채운다.** 자동 점검은 실제 기기가 아니라 기기를 흉내 낸 Chrome에서 돌렸고(아래 "이미 자동으로 본 것"), 그 결과로 이 표의 칸을 대신 채우지 않았다. G1, G2, G3의 "통과"도 자동 점검만으로 쓰지 않는다.

## 쓰는 법

1. 기준 기기를 정해 아래 "기준 기기" 표에 적는다. D-2는 3종을 정하지 않았다. 설계서가 정한 종류는 **가로 태블릿(주), PC(주), 세로 휴대폰(2순위)** 이다. 무음 스위치(S7)를 보려면 아이폰이나 아이패드를 하나 넣는 것이 좋다. 이것은 제안이고, 정하는 것은 사람이다.
2. 점검하는 빌드(미리보기, 또는 공개 채널 빌드)를 "기준 기기" 표에 적는다. 8-5의 공개 조건 점검은 공개 채널 빌드를 쓴다.
3. 칸에 ○(통과), ×(실패, 아래 "발견한 것"에 한 줄), —(해당 없음)을 적는다. ×를 고친 뒤에는 같은 칸을 다시 본다.
4. 점검한 사람, 날짜, 기기와 브라우저 이름을 빠뜨리지 않는다.

## 이 점검표와 자동 점검의 한계

- 자동 점검의 "휴대폰"과 "태블릿"은 화면 크기, 화소 비율, 터치 입력, 모바일 화면 설정을 맞춘 데스크톱 Chrome이다. 실제 아이폰의 Safari, 안드로이드 Chrome의 터치 처리, 주소창과 홈 막대의 실제 움직임, 기기의 소리 장치를 쓰지 않는다.
- 가장자리 여백은 Chrome이 흉내 낸 값(59, 34, 21 px)이다. 실제 기기의 여백은 기종마다 다르고, 주소창이 보이는지에 따라 달라진다.
- 소리 장치를 멈춘 시험은 `AudioContext.suspend()`로 흉내 낸 것이다. 실제 전화나 화면 잠금에서 브라우저가 장치를 어떤 상태(`suspended`나 iOS의 `interrupted`)로 두는지는 기기에 달렸고, 이 앱은 두 상태 모두 "누르면 깨운다"로 같게 다룬다(`running`이 아니면 `resume()`).
- iOS의 무음 스위치를 코드로 무시하는 방법(브라우저의 오디오 세션 종류를 바꾸는 것)은 쓰지 않았다. 설계서 8.6이 정한 것은 "소리가 나지 않을 때 볼 안내 문구"이고(도움 화면에 있다), 기기의 무음 설정을 앱이 거스르지 않는 쪽을 따랐다(D-281).
- 접근성 자동 점검(`a11y8.flow.ts`)은 이름, 크기, 잘림, 글자 대비를 재고, 키보드는 주민 카드 하나만 본다. **화면 낭독기가 실제로 읽는 소리, 눈으로 보는 흑백 화면, 움직임 줄이기, 색 없이 구분은 보지 않는다**(A2~A5). 작업대는 처음 열린 상태만 쟀고 놓고 고르는 동안 바뀌는 상태(틀린 칸, 선택한 칸)는 재지 않았다.
- 조작 막대 표는 작업대를 처음 연 상태(문제를 고르기 전)만 쟀다. 확인을 누르면 '확인 결과' 줄이 커져 막대가 더 높아질 수 있고, 푸는 중과 자유로 놀기의 높이도 다르다(D-205). 막대가 월드를 덮어도 쓸 만한지, 줄어든 월드로 푸는 것이 힘든지는 보지 않았다. 막대의 크기와 틀은 바꾸지 않았다(D-288).
- 프레임 속도(fps)는 이 표에 없다. 자동 점검의 그리기는 소프트웨어(SwiftShader)라서 기준값이 아니다(5-9의 기록). 8-4는 대신 프레임 하나에 우리 코드가 쓰는 시간(ms)과 불러오기 시간, 그림 메모리의 계산값을 재어 `docs/approvals.md`에 적었다. 모두 이 컨테이너의 값이고 기준 기기의 값이 아니다.
