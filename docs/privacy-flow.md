# 개인정보 흐름 (8-2)

설계서 12.11의 8-2("문구 재검토, 개인정보 흐름")와 10.9("서버가 판정하지 않는다. 로그인, 원격 수집이 없다"), D-6("이 기기 안에만 저장, 계정 없음")의 근거 문서다.
이 문서가 말하는 것은 **코드와 실제 Chrome 한 번의 사용으로 확인한 것**과 **확인하지 못한 것**을 나눠 적는다. 법률 검토가 아니다.

## 한눈에

- 이 앱은 이름, 연락처, 생년월일, 녹음, 위치, 기기를 가리키는 값을 받지 않는다. 받는 코드가 없고, 보내는 코드도 없다.
- 진행과 사용 기록은 이 브라우저의 IndexedDB 하나에만 쌓인다. 밖으로 나가는 것은 사용자가 단추를 눌러 내려받는 파일뿐이다.
- 사용자가 글을 적는 곳은 곡 이름 입력칸 둘뿐이다(20글자까지). 그 글은 저장 파일에만 들어가고 사용 기록에는 들어가지 않는다.
- 대상 이용자(D-3)는 아직 정해지지 않았다. 어린이로 정해지면 따로 설계할 것을 아래 "대상 이용자가 어린이로 정해지면"에 적었고, **구현하지 않았다**.

## 받지 않는 것과 그 근거

| 말하는 것 | 근거 | 확인한 곳 |
|---|---|---|
| 통신하는 코드가 없다(fetch, XMLHttpRequest, WebSocket, EventSource, sendBeacon, 서비스 워커, Worker 등) | src의 모든 파일(2백여 개)을 문법 트리로 읽어 그 이름이 하나도 없음을 센다. 주석과 글 속의 낱말은 이름이 아니라서 걸리지 않는다 | `tests/unit/privacy.test.ts` "받는 것이 없다: 통신 코드" |
| 바깥 주소가 없다 | 코드의 글자 상수에 http(s)·ws(s)·`//` 주소가 없다(SVG 이름공간 하나만 있다). index.html과 스타일 파일에도 없다. 아이콘은 data 주소다 | 같은 파일 "받는 것이 없다: 외부 주소" |
| 이름, 연락처, 생년월일, 녹음, 위치, 기기를 가리키는 값을 다루는 이름이 없다 | getUserMedia, MediaRecorder, geolocation, userAgent, email, birthday 같은 이름 33개가 src에 하나도 없다 | 같은 파일 "받지 않는 것" |
| 글을 적는 입력칸은 곡 이름 둘뿐이다 | JSX의 input, textarea, select를 모두 찾아 종류를 적어 둔 표와 맞춘다: 슬라이더, 파일 고르기(저장 가져오기), 곡 이름 입력칸 둘(maxLength 20) | 같은 파일 |
| 실제 Chrome에서 나간 요청은 모두 같은 주소의 읽기(GET)다 | 세계를 열고 지도, 목록, 과제, 설정을 지나는 한 번의 사용에서 요청을 모두 센다. 바깥 주소 0건, GET 외 방식 0건, 글꼴 요청 0건 | `tests/flow/privacy.flow.ts` |
| 웹소켓, 서비스 워커, 쿠키, 캐시 저장소가 없다 | 같은 사용에서 모두 0이다. `document.cookie`도 비어 있다 | 같은 파일 |
| 고지 원문(오픈소스와 글꼴의 라이선스)은 연결이 끊겨도 열린다 | 연결을 끊은 채로 설정의 '정보'를 열어 요청 0개로 원문이 보인다 | 같은 파일, `tests/unit/about-section.test.tsx` |

## 저장하는 것

| 어디 | 무엇 | 언제 | 지우는 길 |
|---|---|---|---|
| IndexedDB `levelup-music-world`의 `save` 칸, 키 `levelup-music-world:v1:save:current` | 진행 전체: 월드 안의 마지막 위치(x, y, 지역, 방향. 현실의 위치가 아니다), 지나간 정거장, 찾은 소리 조각, 연 과제, 놓은 음(도전 초안), 시도 결과, 만든 곡과 그 이름, 설정 8가지, 첫 안내를 봤는지 | 바뀔 때마다 | 브라우저의 사이트 데이터 지우기. 앱 안에는 지우는 단추가 없다 |
| 같은 칸, `save:previous`, `save:next`, `save:unreadable` | 직전 정상 저장, 쓰는 도중의 임시 저장, 읽지 못해 따로 남긴 원본 | 저장이 두 번째로 쓰일 때, 쓰는 도중, 읽지 못했을 때 | 위와 같다 |
| **localStorage**의 `levelup-music-world:v1:save:emergency` | 저장이 끝나기 전에 페이지가 닫히거나 숨겨질 때(앱 전환 포함) 적는 응급 사본. 저장 파일과 같은 내용이다 | 아직 저장하지 못한 바뀐 것이 있을 때만. 다음에 열 때 현재 저장보다 새것이면 현재로 올라간다 | 위와 같다. 저장 가져오기가 끝나면 앱이 지운다 |
| 같은 칸, `levelup-music-world:v1:usage-log` | 사용 기록(사건의 종류, 과제·정거장·설치물의 id, 들어온 길, 확인 결과, 시각). 한도 3000건 | 처음에는 켜져 있다. 설정의 '사용 기록'에서 끄거나 지운다 | 설정의 '기록 지우기'(확인을 거친다), 또는 위와 같다 |
| (IndexedDB를 못 쓸 때) localStorage의 같은 키들, 둘 다 못 쓰면 메모리 | 같은 내용 | 저장소를 못 쓰는 브라우저 | 메모리는 새로 고치면 사라진다 |

실제 Chrome에서 확인한 것: 데이터베이스 하나(`levelup-music-world`), 저장 칸 하나(`save`), 남은 키는 모두 `levelup-music-world:v1:` 접두어가 붙은 정해진 이름이었다. 사용하는 동안 localStorage와 sessionStorage는 비어 있었고, 저장이 끝나기 전에 페이지를 숨기자 localStorage에 `save:emergency` 하나만 적혔다(저장 파일과 같은 필드)(`tests/flow/privacy.flow.ts`). 코드에서는 저장소 API를 만지는 파일이 `src/platform/storage.ts` 하나다(`tests/unit/privacy.test.ts` "저장하는 곳이 정해져 있다").

저장은 한 브라우저 프로필 안에 있다. 같은 기기와 브라우저를 함께 쓰는 사람은 서로의 진행을 볼 수 있다(계정이 없다).

## 사용자가 글을 적는 곳

곡 이름(`src/ui/panels/song/MelodyAside.tsx`, `src/ui/notebook/NotebookPages.tsx`)이 유일하다. 20글자까지이고 앞뒤 공백을 지우고 안의 공백은 하나로 줄인다. 사용자가 이름을 적을 수 있으므로 **곡 이름에는 개인 정보가 들어갈 수 있다.** 그 글이 가는 곳:

- 저장소의 `save:*` 키와 응급 사본(이 기기 안)
- 사용자가 '저장 내보내기'를 눌러 받는 저장 파일
- 사용 기록에는 들어가지 않는다. 사용 기록의 사건 필드는 닫힌 목록이다(아래).

## 나가는 것

| 무엇 | 어떻게 | 담긴 것 |
|---|---|---|
| 앱 파일과 월드 그림 파일 | 브라우저가 같은 주소에서 읽는다(GET) | 앱이 보내는 데이터는 없다. 요청 자체(주소, 시각, 브라우저 종류)는 호스팅 서버에 보인다(한계 참고) |
| 저장 파일 `levelup-music-world-save-날짜.json` | 사용자가 '저장 내보내기'를 누른다 | 위 표의 `save:current` 내용 그대로. 맨 위 필드 10개, 탐험 상태 6개, 설정 8개, 선호 2개(정답표 `tests/privacy-fields.ts`) |
| 사용 기록 파일 `levelup-music-world-usage-log-날짜.json` | 사용자가 '기록 내보내기'를 누른다 | 아래 표 |
| 읽지 못한 저장의 원본 `…-unread-날짜.json` | 읽지 못해 따로 남긴 원본이 있을 때만 나오는 단추 | 저장 원본(저장 파일과 같은 종류) |

'저장 가져오기'는 사용자가 고른 파일을 이 기기에서 읽을 뿐 어디로도 올리지 않는다.

**사용 기록 파일의 사건 필드**(코드가 이 목록 밖의 필드를 걸러 내고, 정답표가 이 목록을 따로 들고 있다):

| 사건 | 필드 |
|---|---|
| session-start | screen(처음 열린 화면의 종류) |
| station-enter | stationId, route(걷기·지도·목록·수첩·주소) |
| quest-enter | questId, variantId, route, surface, stationId |
| help-open | kind, what(도움의 이름), questId, variantId |
| return-to-origin | questId, variantId |
| placement-edit, listen | questId, variantId, surface, free, listen은 what(내 것·목표) |
| check | questId, variantId, result, assistUsed |
| stone-step | installationId, slot |
| discovery-found | discoveryId |

모든 사건에 seq, sid(실행 번호), at(시각)이 붙는다. 파일 맨 위에는 format, formatVersion, projectId, exportedAt, note, dropped, summary가 있다. 값은 정해진 이름(id), 고르는 값, 숫자, 날짜뿐이고 공백이나 한글이 들어간 글은 없다. `what`의 값은 코드가 정한 이름이다(`src/app/usage.ts`: 'help', 설치물 id, 도움 설정의 이름 slow·repeat·showCount·ledger·scoped, 도움 연습의 id).

확인한 곳: `tests/unit/privacy.test.ts` "나가는 것: 사용 기록 파일에는 정해진 필드만 있다"(모든 사건 종류, 이름·메일·글·음 목록·기기 값을 얹어 넘긴 경우, 저장소에서 읽은 기록에 끼어 있는 경우), `tests/flow/privacy.flow.ts`(실제 Chrome에서 내려받은 두 파일).

8-2에서 이 시험이 잡은 것: 사용 기록은 형식이 맞는 사건이면 **다른 필드가 끼어 있어도 그대로 두고 내보냈다**(`appendEvent`와 `normalizeUsageLog`가 받은 객체를 펼쳐 썼다). 지금 코드는 이런 필드를 넣지 않지만, 앞으로 사건을 더하다 실수로 이름이나 글이 들어가거나 저장소의 값에 끼어 있어도 파일로 나갔을 것이다. `cleanBody`가 사건 종류별로 정해진 필드만 남기게 고쳤다.

## 한계 (솔직하게)

- 코드 검사는 **이름**으로 본다. `window['fet' + 'ch']` 같은 동적 접근, `eval`, 원격 `import()`는 이름 검사로 못 잡는다(원격 `import()`는 글자 상수 검사가 주소를 잡는다). src 밖의 라이브러리(Phaser, Tone.js, Preact, VexFlow)는 검사하지 않았다. Phaser의 적재기는 월드 그림 파일을 같은 주소에서 읽는다. 실제 Chrome 확인은 한 번의 사용이 지난 길(세계, 지도, 목록, 과제, 설정)만 본다. 합주, 놀이 악기, 설치물을 쓰는 동안의 요청은 이 시험이 보지 않는다.
- **호스팅 서버는 이 앱 바깥이다.** 앱은 아무것도 보내지 않지만, 정적 파일을 받을 때 호스팅 서버는 요청의 주소, 시각, 브라우저 종류, 접속 주소를 남길 수 있다. 호스팅을 고를 때 접속 분석 기능을 끄고 접속 기록의 보관 기간을 확인해야 한다. 이것은 코드로 확인할 수 없어 사람이 한다.
- 보안 머리말(`Content-Security-Policy`, `Referrer-Policy` 등)은 서버가 보내야 하고 이 저장소는 서버를 갖지 않는다(정적 호스팅의 설정이다). 8-5에서 값을 정하고 실제 Chrome으로 시험했다(`docs/hosting.md`): `default-src 'self'` 하나로는 월드가 그려지지 않아서 Phaser의 기본 그림(data 주소)과 그림 파일(blob 주소), VexFlow의 악보 글꼴(data 주소), Tone.js의 시계 작업자(blob 주소) 네 가지만 열었다. 앱이 부르는 곳은 같은 주소뿐이라 `connect-src 'self'`로 브라우저가 지키게 한다. 같은 머리말을 보내는 **시험 서버에서만** 확인했다: 실제 호스팅, HTTPS, 사파리와 파이어폭스는 사람이 본다.
- 사용 기록은 **처음에 켜져 있다.** 사용 관찰(G1)을 위해서다. 대상이 정해지면(D-3) 기본값을 다시 정해야 한다.
- 앱 안에는 **진행을 지우는 단추가 없다.** 공유 기기에서는 브라우저의 사이트 데이터를 지워야 한다.
- 저장 형식 판이 오르는 날(지금은 1판뿐)을 위해, 판이 오른 앱은 새 키가 비어 있을 때 옛 판의 키를 읽기만 해서 이어 받는다(8-6, `docs/operations.md`). 옛 키는 앱이 지우지 않으므로 기기에 옛 판의 기록이 남는다. 설정의 '기록 지우기'는 옛 판의 사용 기록도 함께 지우고, 진행(저장)의 옛 키는 지우는 단추가 없어 브라우저의 사이트 데이터 지우기로만 사라진다.
- 곡 이름 입력칸 옆에 "이름이나 연락처를 쓰지 마세요" 같은 안내가 **없다.** 곡 이름은 자유로운 글이다.
- 문구가 7.6과 W-9에 맞는지는 글자 모양 점검(`npm run copy`)만 자동이다. 말뜻과 읽기 수준은 사람이 검수표로 본다(아래).

## 대상 이용자가 어린이로 정해지면 (D-3, 설계만 — 구현하지 않음)

**전제:** 지금은 대상이 정해지지 않았다. 8-2의 조건 "대상 이용자가 정해졌으면"이 아직 참이 아니다. 아래는 그날 바로 일을 시작할 수 있게 적어 둔 설계이며, 지금 코드는 이것을 하지 않는다.

**확인해야 할 법적 틀(법률 검토가 아니다):** 개인정보 보호법 제22조의2(아동의 개인정보 보호)는 만 14세 미만 아동의 개인정보를 처리하려면 법정대리인의 동의를 받고 그 동의를 확인하도록 하며, 동의를 받기 위한 최소한의 정보는 아동에게서 직접 받을 수 있고, 아동에게 알릴 때는 쉬운 양식과 알기 쉬운 언어를 쓰도록 한다. 이 앱은 개인정보를 받지 않으므로 **동의가 필요한 '처리'가 있는지부터** 따져야 한다. 기기 안 저장이 처리인지, 사용 기록 파일을 관찰자가 가져가는 순간 누가 처리 주체가 되는지는 법률 검토가 정할 일이다. 호스팅 서버의 접속 기록도 같이 본다.

**설계 후보(그날 정할 것):**

1. **사용 기록(관찰용)의 기본값을 끈다.** 파일이 관찰자에게 넘어가는 경우에만 동의 문제가 생긴다. 켜는 것은 보호자나 관찰자가 한다.
2. **앱 안에서 나이를 묻거나 동의를 받지 않는다.** 앱에는 계정이 없고 생년월일을 받지 않는다(10.9). 나이를 묻는 단계는 W-9("나이를 추정하지 않는다")와도 어긋난다. 동의는 관찰 운영(앱 밖의 동의서)에서 받고, 앱은 사용 기록을 켜는 자리에 "보호자와 함께 켜 주세요" 같은 사실 안내만 둔다.
3. **문구 전체를 다시 검토한다**(7.6). 입력은 `npm run copy -- --deck 경로`로 만든 검수표다. 읽기 수준은 사람이 정한다.
4. **곡 이름 입력칸 옆에 안내를 둔다**(이름이나 연락처를 쓰지 않는다는 한 문장). 저장 파일에 곡 이름이 들어가기 때문이다.
5. **앱 안에서 진행 지우기**(확인을 거치는 단추)를 더한다. 학교나 가정의 공유 기기를 쓰는 경우를 위해서다.
6. 호스팅의 접속 분석을 끈다. 보안 머리말은 8-5에서 정했다(`docs/hosting.md`).

**그날 바뀌는 시험:** 사용 기록 기본값을 정하는 시험(`usagelog` 단위 시험의 "처음에는 켜져 있는 빈 기록")과 이 문서의 한계 목록이 달라진다.

## 사람이 확인할 것

- 법률 검토: 개인정보 보호법 적용 여부(특히 대상 이용자가 정해지면), 호스팅 서버의 접속 기록과 보관 기간.
- 호스팅 설정: 접속 분석 끄기, 접속 기록의 보관 기간 정하기, `docs/hosting.md`의 보안·캐시 머리말이 **실제 호스팅의** 응답에 붙는지 보기(8-5는 같은 머리말을 보내는 시험 서버에서 Chrome 하나로만 시험했다. HTTPS의 `Strict-Transport-Security`, 사파리, 파이어폭스는 못 봤다).
- 사용 기록이 처음에 켜져 있어도 되는가(관찰 계획과 함께).
- 실제 기기에서: 설정의 '정보'(고지 원문 열기, 글자 읽기), 저장·기록 내려받기(특히 iOS Safari의 내려받기).
- 문구 검수표(`npm run copy -- --deck 경로`)를 읽고 7.6과 W-9에 맞는지 판단하기. 대상이 정해지면 읽기 수준까지.
